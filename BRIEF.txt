# ROLE
You are a senior full-stack engineer and UI/UX designer. Build "RozgarLink", a working,
demo-ready Skills-to-Opportunity Matching web app for a 12-hour hackathon (government/GovTech
domain). Judges will test it live, so it must run locally with one command, with no paid APIs.

# PRODUCT SUMMARY
Two portals in one app:
1. COMPANY PORTAL: companies post opportunities, define compulsory skills (eligibility) and
   point-weighted skills (ranking), and set tier cut-offs.
2. APPLICANT PORTAL: applicants build a profile, add skills and certificates, see eligible
   jobs, their Tier, skill gaps, learning paths, progress, and daily check-ins.

# NON-NEGOTIABLE RULES (from the problem statement - the app will be judged on these)
1. Eligibility is separate from ranking. A compulsory skill/qualification/location rule that a
   candidate fails makes the opportunity "Not Eligible", however good the other skills are.
   Only eligible opportunities are ranked and given a Tier.
2. Eligibility is decided ONLY by explicit rules stated by the opportunity (deterministic code).
   AI/NLP may extract skills, judge skill similarity (e.g. "ReactJS" = "React.js" = "React")
   and inform RANKING only. It must never decide eligibility.
3. Every result is explained in plain language: why an eligible job ranks where it does (points
   breakdown) and exactly which condition a rejected candidate fails.
4. Skill gaps and learning pathways come from a local, team-supplied JSON course catalogue.
   Never call a live course provider.
5. Any change to the candidate's skills, qualifications, certificates or location must instantly
   recompute eligibility, points, tiers and rankings, with a visible "what changed" highlight.
6. Show a disclaimer: "Results are decision support. Criteria used are those stated by each
   opportunity."
7. Use fictional data only. Provide a local fallback so the app works fully offline; any
   external AI is optional and the core demo must not depend on it.

# TECH STACK (keep it fast to build)
- Frontend: React + Vite + Tailwind CSS (or Next.js if you prefer), responsive, mobile-first.
- State/storage: localStorage or a small SQLite/JSON backend (Express/FastAPI). Seed with demo data.
- Matching engine: pure, unit-testable functions in a separate module (no UI logic inside).
- Skill matching fallback: a local synonym dictionary + normalization (lowercase, strip
  punctuation) + fuzzy string match (Levenshtein/Jaro-Winkler). Optional embeddings/LLM can be
  added behind a toggle with this fallback as default.

# DESIGN REQUIREMENTS
- Modern, clean, trustworthy GovTech look: card-based layout, rounded corners, soft shadows,
  a calm primary colour (indigo/teal), clear typography, light and dark mode.
- Colour-coded tiers: Tier 1 = green/gold, Tier 2 = blue, Tier 3 = orange. Not eligible = grey/red.
- Sticky top navbar with a role switch (Company / Applicant), clear icons, tooltips, empty
  states, loading states, and accessible contrast. Easy for first-time users: max 3 clicks to
  any main feature, plus a short onboarding stepper.
- Optional language toggle (English / Hindi / Marathi) for key labels.

## STEP 2 - Matching engine (core, build this first and test it)
Implement as pure functions with unit tests:
1. normalizeSkill(text) and skillSimilarity(a, b) -> 0..1, using synonyms + fuzzy matching.
   A match counts when similarity >= a configurable threshold (default 0.8); show the matched
   alias to the user ("Your 'ReactJS' matched required 'React' - 92%").
2. checkEligibility(applicant, opportunity) -> { eligible: boolean, passed[], failed[] }
   - Fails if ANY compulsory skill is missing, the minimum qualification is not met, or the
     location rule is not met. Each failure includes a plain-language reason, e.g.
     "Missing compulsory skill: SQL", "Requires B.E./B.Tech; you have Diploma".
   - Uses deterministic rules only. No AI input.
3. scoreApplicant(applicant, opportunity) -> only for eligible candidates.
   Points = sum over scored skills of (company points x match strength x level factor).
   Return a full breakdown per skill.
4. assignTier(score, cutoffs) -> Tier 1 (>= tier1Min), Tier 2 (>= tier2Min), Tier 3 (below).
   Tiers are PER OPPORTUNITY, and an overall applicant tier is computed from the average
   of their best eligible matches.
5. explain(result) -> readable sentences: why the job is ranked here, what points came from
   where, and what would move them up a tier ("You need 12 more points for Tier 2: learn Docker
   (+8) and Git (+5)").
6. skillGap(applicant, opportunity) -> missing compulsory skills, missing scored skills, and
   points to be gained.
7. recommendPath(gaps, catalogue) -> ordered learning steps from the local catalogue, shortest
   path first (compulsory gaps first, then highest-points skills), with total estimated duration.
Every recompute must be triggered automatically on any profile change.
